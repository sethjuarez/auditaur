Human output is compact and bounds table cells. JSON output uses camelCase fields matching the Rust model.

`init skill` installs the Auditaur agent skill into `.github/skills/auditaur-debug/SKILL.md` for a consuming repository. Use `--path <repo-root>` to target another repo and `--force` to overwrite an existing skill. The skill teaches Copilot/agents the recommended Auditaur debug readiness, attach-vs-wrapper startup choice, CDP, screenshot/snapshot, telemetry, and cleanup workflow. After the skill is available from the Auditaur repository on GitHub, users with GitHub CLI skill support can also install it with `gh skill install sethjuarez/auditaur auditaur-debug`. `--since` accepts durations such as `30s`, `10m`, `2h`, or `1d`. `timeline` merges logs, spans, span events, frontend errors, IPC calls, events, and window states into one chronological view. `related` returns the correlated structured rows behind trace, run, window, session, and recent-activity investigations. `agent-runs` groups agentive-style spans by run id and surfaces trace id, root command, model/tool call counts, provider/model, status, duration, logs, errors, and final summary when present. `agent-run <run-id>` drills into the grouped model calls, tool calls, agent events, logs, IPC calls, and errors for a run; `--app <name>` resolves a discovered app such as `cutready` without manually passing `--db`. `explain` summarizes obvious failures. `exceptions` groups captured frontend exceptions, Rust panic-hook records, and failed IPC calls by stable fingerprint. Use `--fingerprint <id>` to drill into one group, `--markdown` for a GitHub issue-ready draft, and `--output <path>` to write the JSON or Markdown report to disk; review and redact the local report before posting it publicly. `bundle` always redacts share-sensitive JSON fields and exports bounded JSON suitable for bug reports or handoffs; `--redacted` is accepted for explicitness.

`apps` reads discovery files from the local Auditaur data directory and marks entries stale when the heartbeat is older than 30 seconds. Stale entries for the same app identity are annotated with `supersededBySessionId`, `secondsUntilNextStart`, `churnSessionCount`, `churnWindowSeconds`, and `churnHint` when newer sessions appear after them. This helps distinguish a normal app exit from likely restart/session churn, such as a Tauri dev watcher rebuild after source edits, and highlights repeated restart bursts within a short window. `health` summarizes active/stale app health from heartbeat freshness, session churn hints, database readability/schema validation, and collector capability version skew; stale apps are surfaced but do not fail the overall report. `debug` exposes an agent-friendly readiness timeline. Prefer attach mode for human/local debugging: start the app normally, then run `debug watch --until-ready`. Use `debug run -- <command>` for agent-owned or dogfood smoke validation where Auditaur should start the normal app command and watch the same milestones. The timeline distinguishes app discovery, heartbeat freshness, database/schema readiness, session rows, window telemetry, backend/plugin telemetry, optional frontend telemetry, and optional CDP endpoint readiness. Pass `--require-frontend` when the session should not be considered ready until frontend logs/errors/IPC/events are observed; pass `--cdp-port` when WebView/driver readiness matters. JSON output is suitable for agents and includes `ready`, `stages`, `telemetry`, `cdp`, and `hints`.

`drive` is an optional app-driver layer, not part of the read-only observability core: it resolves an observed app session, prints PID/service/session/database attach info, probes localhost Chrome DevTools Protocol ports, lists `/json/list` page targets, and records the telemetry attributes driver actions must emit. In dogfood/dev environments with many historical sessions, use `--session-id`, `--instance-id`, `--pid`, `--latest`, or `--active` to disambiguate; ambiguity errors include top matching sessions and concrete selectors. Drive parent flags are global, so options such as `--json`, `--app`, and `--cdp-port` may appear before or after the subcommand. `drive inspect` prints available CDP targets and attempts to bind them to observed Auditaur window telemetry by exact window title or URL match; unmatched targets stay `unverified`, and single-window/single-target sessions are only marked `probable`. It also reports target ownership separately: `matched_window_telemetry` means the target matched observed window title/URL telemetry but PID/session ownership is not independently proven yet, while `probable_unproven` means the association comes only from single-window/single-target context. `drive wait --selector <css>` connects to the selected target WebSocket and waits with CDP `Runtime.evaluate(Boolean(document.querySelector(...)))`; it is intentionally non-mutating, requires an explicit `--cdp-port`, auto-selects only an unambiguous or evidence-bound target, and exits non-zero on timeout. CDP auto-probing keeps default port scans short, while explicit `--cdp-port` probing waits up to two seconds and reports probe failures, such as connection, HTTP status, or invalid JSON errors, in `cdp.reason`.

Driver actions use a stable JSON envelope with `action`, `selector`, `serviceName`, `sessionId`, `targetId`, `windowLabel`, `targetBindingStatus`, `targetOwnershipStatus`, `ownershipProven`, `mutatesApp`, `payload`, optional `testId`/`stepId`, and `telemetryAttributes` keys for future correlation (`auditaur.test_id`, `auditaur.step_id`, `auditaur.driver.action`, `auditaur.driver.selector`, target id, target binding/ownership status, ownership proof flag, window label, trace id, and span id). `exists`, `text`, and `screenshot` are diagnostic/read-style actions; `screenshot --snapshot-output <path>` is explicit opt-in failure artifact mode and writes a bounded JSON page snapshot/manifest alongside the PNG for failure handoffs. The snapshot clips page text and HTML fields to 65,536 characters each, may include sensitive DOM content or URLs, and should be reviewed before sharing. `click`, `fill`, and `press` are the first mutating actions. If a mutating action selects a target where `ownershipProven` is `false`, it fails unless `--allow-unproven-target` is supplied to acknowledge that Auditaur has not proven endpoint PID/session ownership. The older `--allow-probable-target` flag is accepted as a hidden compatibility alias. These actions currently use DOM-level CDP `Runtime.evaluate` semantics: `click` calls `element.click()`, `fill` sets `value` and dispatches `input`/`change`, and `press` dispatches synthetic `keydown`/`keyup` events against the selector or active element. That makes them useful for smoke tests and CutReady-style validation, but they are not yet a full Playwright input stack and do not persist action telemetry into the Auditaur SQLite store.

For Tauri/WebView2, launch the app with remote debugging enabled, for example `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9222"`, then run `auditaur drive --app <name>` or pass `--cdp-port <port>`. Staleness is heartbeat-only today; platform-specific PID existence checks are not implemented yet. `doctor --db` validates a specific SQLite database; `doctor` without `--db` validates discovery files and readable database paths. `doctor tauri` checks a Tauri app for the Auditaur crate, plugin registration, and required capability permission.
